# Дизайн: главная страница со слотами и общий header

## Статус

- Согласовано: 18.10.2026.
- Обновлено: 18.10.2026 — занятые слоты видны в расписании; для `admin`/`super_admin` показываются данные владельца и ссылка на `/admin/bookings/[id]`; для `guest`/`user` — только `Занято` без PII.
- Реализация: не начата; документ фиксирует согласованный объём до правок UI.
- Ограничения этапа: не менять модели, роли, статусы, auth-контур и цветовую палитру.

## 1. Задача

Сделать `/` полезной точкой входа, а не только приветственной страницей:

- показывать слоты на 7 дней вперёд всем посетителям, включая гостей;
- показывать одну и ту же таблицу расписания на `/` и `/slots`;
- дать гостю понять, что для записи нужно войти или зарегистрироваться;
- заменить разрозненные ссылки на страницах единым `header` с навигацией по ролям.

Текущее состояние: `/` — статическая приветственная страница; `/slots` требует сессию и выводит список карточек; общего `header` нет. Новый дизайн не меняет серверные правила бронирования: они остаются в существующих Server Actions и `app/lib/*`.

## 2. Принятые решения

- **Вариант A:** `/` и `/slots` используют один и тот же компонент `ScheduleTable` и одну серверную подготовку данных. Различаются только метаданные и активный пункт навигации; отдельные компоненты для ролей не создаются.
- Публичное расписание показывает **все будущие слоты** горизонта: и свободные, и занятые. Занятые слоты не скрываются из таблицы.
- `guest` и `user` видят для занятого слота только неинтерактивный статус `Занято`. Данные владельца (email, отображаемое имя, идентификатор) в их разметку не попадают.
- `admin` и `super_admin` видят в занятой ячейке владельца активной брони: отображаемое имя (если задано), email, `User.id` и ссылку на `/admin/bookings/[id]`. Ссылка открывает детализацию брони, а не создаёт бронь.
- Гость при клике по свободному слоту получает модальное окно входа/регистрации; бронь не создаётся.
- `user`, `admin` и `super_admin` после клика по свободному слоту видят подтверждение, затем создаётся бронь `pending` и происходит переход на `/bookings`.
- Администратор может записаться на свободный слот для себя так же, как `user`; управление слотами и бронями остаётся в `/admin`.
- Цветовую палитру не меняем: используем текущие нейтральные стили проекта и поддержку тёмной темы. Терракотовые оттенки из макетов в этом этапе не переносим.
- `<header>` размещается в `<body>`, а не в HTML `<head>`: в `<head>` нельзя размещать интерактивные кнопки и навигацию.
- Новые модели, миграции, роли, статусы и зависимости не добавляются. Новыми в реализации являются серверная функция расписания с ролевым DTO и защищённая страница `/admin/bookings/[id]`.

## 3. Общий header

### 3.1. Состав

Слева — название/логотип «Mini Booking System», ведущий на `/`. Справа — навигация. На узких экранах пункты переносятся на вторую строку или прокручиваются по горизонтали без изменения порядка.

### 3.2. Матрица видимости

| Пункт | guest | user | admin | super_admin | Куда ведёт |
|---|---:|---:|---:|---:|---|
| Расписание | да | да | да | да | `/slots` |
| Мои записи | нет | да | да | да | `/bookings` |
| Уведомления | нет | да | да | да | `/notifications` |
| Администрирование | нет | нет | да | да | `/admin` |
| Аккаунт | нет | да | да | да | `/account` |
| Войти | да | нет | нет | нет | `/login` |
| Выйти | нет | да | да | да | Server Action `logout` |

Пункт «Регистрация» отдельной кнопкой в `header` не выводится: он доступен со страницы `/login` и из гостевого модального окна. Это соответствует согласованной матрице; добавление отдельного пункта — отдельное решение.

Пункт называется «Расписание», а не «Свободные слоты»: таблица показывает и свободные, и занятые слоты. Ссылка `/admin/bookings/[id]` не является отдельным пунктом `header`; она открывается из ячейки расписания и из карточки брони на `/admin/bookings`.

### 3.3. Поведение

- Видимость пунктов определяется на сервере по действующей сессии и роли; роль не принимается из query-параметра или клиентского состояния.
- Текущий раздел подсвечивается: `/` и `/slots` — «Расписание»; `/bookings` — «Мои записи»; `/notifications` — «Уведомления»; `/admin`, `/admin/slots`, `/admin/bookings` и `/admin/bookings/[id]` — «Администрирование»; `/account` — «Аккаунт».
- «Выйти» — форма с Server Action `logout`, а не GET-ссылка. После выхода пользователь попадает на `/login`.
- `header` не содержит форм входа и не дублирует проверку ролей: защита остаётся на страницах и в серверных модулях.

### 3.4. Мобильная версия

- Навигация не скрывается в бургер на этом этапе: пункты переносятся или прокручиваются, чтобы все доступные роли действия оставались видимыми.
- Высота и отступы `header` не должны «прыгать» после загрузки сессии: для области сессии предусмотреть нейтральный placeholder.

## 4. Главная страница `/` и `/slots`

### 4.1. Одинаковое содержимое

Обе страницы используют один компонент расписания и одну логику подготовки данных. Разница только в метаданных и активном пункте навигации; дублировать разметку таблицы нельзя.

Структура страницы:

```text
<header> логотип | навигация по роли </header>
<main>
  <h1>Расписание</h1>
  <p>Все будущие слоты на 7 дней вперёд. Время указано в UTC.</p>
  <ScheduleTable />
</main>
```

- Заголовок и пояснение видны и гостю, и авторизованному пользователю.
- Время отображается в UTC — это действующее правило проекта; локальная таймзона в этом этапе не вводится.
- Ссылки «Мои записи», «Аккаунт», «На главную» из старой карточки `/slots` убираются из тела страницы: их заменяет `header`.
- Таблица показывает все будущие слоты горизонта, включая занятые. Скрывать занятые слоты или заменять их пустыми ячейками нельзя.

### 4.2. Источник данных

- Для `/` и `/slots` используется одна серверная функция `listUpcomingSchedule(viewer)` в `app/lib/slots.ts`. Она возвращает все будущие слоты горизонта 7 дней, отсортированные по `startsAt`, с числом активных броней (`pending` + `confirmed`) и свободной вместимостью. `availableCapacity = capacity - activeBookings`, но не ниже нуля.
- `listUpcomingSlots()` остаётся для существующих потребителей (например, `/admin/slots`) и не расширяется данными владельцев. Публичное расписание использует новый ролевой DTO.
- DTO для `guest` и `user` содержит только `id`, `startsAt`, `endsAt`, `capacity`, `activeBookings`, `availableCapacity`, `isUpcoming`. Полей владельца и массива броней в нём нет.
- DTO для `admin` и `super_admin` дополнительно содержит активные брони слота: `bookingId`, `ownerId`, `ownerEmail`, `ownerDisplayName` (может быть `null`) и `status`. Отменённые брони в DTO не попадают.
- Роль для выбора DTO определяется на сервере по действующей сессии; параметр `role`, `isAdmin` или иной признак из query-параметра, формы или тела запроса не принимается. Для авторизованного viewer роль повторно читается из базы перед выборкой данных владельцев.
- В расписание попадают все слоты горизонта, у которых `startsAt > now`. Прошедшие слоты не показываются. Занятые слоты показываются со статусом `Занято`.
- `/slots` больше не требует сессию: страница доступна гостю. Защищёнными остаются `/bookings`, `/notifications`, `/account` и `/admin/*`.
- Сессия для `header` читается на сервере через `getCurrentUser()`; отсутствие сессии — нормальное состояние гостя, а не ошибка доступа.

### 4.3. Таблица расписания

**Строки** — календарные даты горизонта по возрастанию. Подпись строки: день недели и дата, например `Понедельник, 28.05`. Дата нужна потому, что горизонт в 7 суток может пересекать границу недели и содержать одинаковые названия дней.

**Колонки** — уникальные интервалы времени, в которых есть хотя бы один слот: свободный или занятый. Например, при слотах `10:00–11:00` и `15:00–16:00` будут только две колонки; диапазоны `00:00–09:00` и `18:00–24:00` не создаются. Колонки сортируются по времени начала, затем по времени окончания.

**Ячейки:**

- если на дату и интервал есть слот с `availableCapacity > 0` — выводится кнопка `Записаться`;
- если у слота `availableCapacity > 1`, на кнопке дополнительно показывается `Свободно: N`;
- если слот полностью занят (`availableCapacity === 0`), для `guest` и `user` выводится неинтерактивный текст `Занято`; кнопки, ссылки и данные владельца отсутствуют;
- если слот полностью занят, для `admin` и `super_admin` выводятся текст `Занято` и список активных броней: `displayName` (или `Без имени`), email, `User.id` и ссылка `Открыть бронь` на `/admin/bookings/[id]`;
- если у администратора слот занят частично (`availableCapacity > 0`, но `activeBookings > 0`), рядом с кнопкой `Записаться` показывается список активных броней; элементы списка — отдельные ссылки и не открывают модальное окно записи;
- собственная активная бронь пользователя на полностью занятом слоте также показывается как `Занято`; детали доступны на `/bookings`;
- если слота нет — ячейка остаётся только структурной `<td>` без текста, кнопки, ссылки, фона и рамки; кликабельного элемента нет.

**Правила раскрытия данных:**

- Для `guest` и `user` серверный DTO не содержит владельца и массива броней; скрытие данных только через CSS недопустимо.
- Для `admin` и `super_admin` в расписании показываются только активные брони (`pending`, `confirmed`) и только те поля, которые перечислены выше. `passwordHash`, `tokenHash` и служебные поля не передаются. На `/admin/bookings` и `/admin/bookings/[id]` владелец отображается и у отменённой брони.
- Ссылка на `/admin/bookings/[id]` ведёт на защищённую страницу детализации; она не является формой и не меняет статус брони.

**Матрица состояний ячейки:**

| Состояние слота | `guest` | `user` | `admin` / `super_admin` |
| --- | --- | --- | --- |
| Свободен, `availableCapacity > 0` | Кнопка `Записаться` → окно входа/регистрации | Кнопка `Записаться` → подтверждение | Кнопка `Записаться` → подтверждение; при частичной занятости рядом список активных броней |
| Полностью занят, `availableCapacity === 0` | Текст `Занято`, без клика и ссылок | Текст `Занято`, без клика и ссылок | `Занято` + владелец каждой активной брони + ссылка на `/admin/bookings/[id]` |
| Слота нет | Пустая `<td>` без контента | Пустая `<td>` без контента | Пустая `<td>` без контента |

**Матрица данных DTO:**

| Поле | `guest` / `user` | `admin` / `super_admin` |
| --- | --- | --- |
| `id`, `startsAt`, `endsAt`, `capacity`, `activeBookings`, `availableCapacity`, `isUpcoming` | да | да |
| `bookingId`, `ownerId`, `ownerEmail`, `ownerDisplayName`, `status` активной брони | нет | да |
| `passwordHash`, `tokenHash` | нет | нет |

**Строки без слотов** не выводятся. Если слотов нет во всём горизонте, вместо таблицы показывается сообщение: «На ближайшие 7 дней слотов нет».

Если у пользователя уже есть активная бронь на частично занятый слот (`availableCapacity > 0`, возможно только при `capacity > 1`), кнопка остаётся, но сервер вернёт `DUPLICATE_ACTIVE_BOOKING`. Отдельное состояние «Вы записаны» в текущий объём не входит; свои брони видны на `/bookings`.

**Семантика:** используется настоящая `<table>` с `<caption>` (визуально скрытым или видимым), `<thead>`, `<tbody>`, `<th scope="col">` для времени и `<th scope="row">` для даты. Это даёт корректную навигацию скринридером и сохраняет выравнивание ячеек.

Пример для текущего seed (14 слотов, 10:00 и 15:00 UTC, capacity = 1). Для `guest` и `user`:

| День | 10:00–11:00 | 15:00–16:00 |
|---|---|---|
| Понедельник, 19.10 | Записаться | Занято |
| Вторник, 20.10 | Записаться | Записаться |

Для `admin` и `super_admin` в занятой ячейке дополнительно выводятся владелец и ссылка:

```text
Занято
Иван Петров · ivan@example.com · cm...owner
Открыть бронь → /admin/bookings/cm...booking
```

`displayName` может отсутствовать — тогда выводится `Без имени`; email, `User.id` и ссылка на бронь остаются. Пример условный: конкретные даты и доступность берутся из базы, а не из документа.

### 4.4. Адаптивность

- На широком экране таблица занимает доступную ширину карточки.
- На узком экране таблица прокручивается по горизонтали; первый столбец с датой остаётся видимым (sticky), а заголовок времени остаётся читаемым.
- Кнопки остаются достаточно крупными для касания; горизонтальный скролл не должен перехватывать вертикальную прокрутку страницы.
- Пустые ячейки не создают визуального «шахматного» фона.

## 5. Клик по слоту

### 5.1. Гость

1. Гость нажимает кнопку «Записаться» в свободной ячейке (`availableCapacity > 0`).
2. Поверх страницы открывается модальное окно с затемнённым фоном.
3. В окне: выбранные дата и время, короткий текст «Чтобы записаться, войдите или зарегистрируйтесь», кнопки «Войти», «Зарегистрироваться», «Отмена».
4. «Войти» ведёт на `/login`, «Зарегистрироваться» — на `/register`, «Отмена» закрывает окно.
5. Запрос на создание брони не отправляется. Прямой POST в `createBookingAction` без сессии по-прежнему отклоняется сервером.
6. Занятая ячейка `Занято` не является кнопкой и не открывает модальное окно.

Выбранный слот между страницами входа и главной не сохраняется. После входа или регистрации текущий auth-контур переводит пользователя на `/account`; чтобы записаться, он открывает `/` или `/slots` заново и выбирает слот. Автоматическое возвращение к слоту и параметр `next` — отдельный шаг, в текущий объём не входят.

### 5.2. Авторизованный пользователь

1. `user`, `admin` или `super_admin` нажимает «Записаться» в свободной ячейке.
2. Открывается модальное окно подтверждения с датой, временем и кнопками «Записаться» / «Отмена».
3. «Отмена», `Esc` или клик по затемнённому фону закрывают окно без запроса.
4. «Записаться» отправляет форму с единственным полем `slotId` в существующий `createBookingAction`.
5. При успехе создаётся бронь `pending`, и действие переводит на `/bookings`.
6. При ошибке (`SLOT_FULL`, `DUPLICATE_ACTIVE_BOOKING`, `SLOT_IN_PAST`, `SLOT_NOT_FOUND`) окно остаётся открытым и показывает понятный текст из Server Action.
7. Занятая ячейка для `user` неинтерактивна: модальное окно не открывается, чужие данные не показываются. Свои брони и их статусы доступны на `/bookings`.

### 5.3. Администратор

- `admin` и `super_admin` бронируют для себя так же, как `user`: владелец берётся из сессии, а не из формы.
- В занятой ячейке администратор видит активные брони с владельцем и ссылкой на `/admin/bookings/[id]`. Ссылка и кнопка `Записаться` — разные интерактивные элементы; переход по ссылке не открывает модальное окно и не создаёт бронь.
- Отдельного выбора пользователя в расписании нет. Управление слотами и подтверждение/отмена чужих броней остаются в `/admin`.

### 5.4. Детализация брони администратора `/admin/bookings/[id]`

- Маршрут доступен только `admin` и `super_admin`. Страница вызывает `requireRole(['admin', 'super_admin'])` до чтения данных, затем `getAdminBooking(actor, bookingId)`.
- Функция `getAdminBooking` повторно проверяет роль по базе и принимает только `bookingId` из параметра маршрута. Для неизвестного идентификатора функция возвращает `null`, а страница вызывает `notFound()`; данные другого пользователя не подставляются.
- Страница показывает: слот (дата, время, вместимость), статус, `createdAt`, `confirmedAt`, `cancelledAt`, email владельца, отображаемое имя (если задано) и `User.id`.
- Действия подтверждения и отмены используют существующие `confirmBookingAction` и `adminCancelBookingAction` и принимают только `bookingId`. Формы не содержат `userId`, роль или новый статус.
- Страница `/admin/bookings` получает ссылку на детализацию в каждой карточке; расписание ведёт на ту же страницу из занятой ячейки.
- Прямой запрос страницы под `user` или гостем уводит на `/access-denied` до чтения данных.

## 6. Модальные окна

- Используется нативный `<dialog>` с `showModal()`: он даёт затемнение через `::backdrop`, удержание фокуса и закрытие по `Esc` без новой зависимости.
- Атрибуты: `role="dialog"` (у нативного `dialog` уже есть), `aria-modal="true"`, `aria-labelledby` на заголовок, `aria-describedby` на описание.
- Клик по фону закрывает окно; клик внутри окна — нет.
- После закрытия фокус возвращается на кнопку слота, которая открыла окно.
- В открытом окне нет полей `userId`, `role`, `status`: только `slotId` для подтверждения записи.
- Ошибка Server Action показывается внутри окна и объявляется через `aria-live="polite"`.
- На время отправки кнопка подтверждения блокируется и показывает «Запись…».
- Занятые ячейки модальных окон не открывают. Ссылки на детализацию брони в административной ячейке не являются частью формы записи.

## 7. Состояния и ошибки

- **Загрузка сессии/расписания:** нейтральный текст «Загрузка расписания…»; без пустой таблицы и без мигания гостевой навигации.
- **Нет слотов в горизонте:** сообщение «На ближайшие 7 дней слотов нет» вместо таблицы.
- **Все слоты заняты:** таблица показывается; в занятых ячейках `Занято`, для администратора — владелец и ссылка на детализацию.
- **Ошибка загрузки данных:** стандартная страница ошибки Next.js; не подменять её вымышленными слотами.
- **Слот стал недоступен после открытия окна:** серверный слой возвращает ошибку, окно показывает её; список обновится после перехода или повторного запроса.
- **Неизвестная бронь на `/admin/bookings/[id]`:** `notFound()` без подстановки чужих данных.
- **Гость или `user` на `/admin/bookings/[id]`:** `/access-denied` до чтения данных.
- **Гость пытается открыть защищённый маршрут:** поведение существующих страниц не меняется (переход на `/access-denied`).

## 8. Доступность и адаптивность

- Таблица имеет доступное имя через `<caption>`; заголовки строк и колонок связаны с ячейками.
- Кнопка слота имеет `aria-label` с датой, временем и остатком мест, даже если визуально время находится в заголовке колонки.
- Все действия доступны с клавиатуры; фокус видим; порядок фокуса совпадает с визуальным.
- Модальное окно удерживает фокус и закрывается по `Esc`; после закрытия фокус возвращается на инициатора.
- Цвет не является единственным признаком доступности: статус и текст кнопки читаются без цвета.
- Тёмная тема сохраняется; контраст текста и кнопок не ниже текущих значений проекта.

## 9. Технические ограничения реализации

- Новые модели, миграции, роли, статусы и зависимости не добавляются.
- `/` и `/slots` читают слоты на сервере через `listUpcomingSchedule(viewer)`; сессия читается через `getCurrentUser()` и не определяет право на просмотр расписания. Она определяет только состав DTO: гостю и `user` — без владельцев, администратору — с владельцами активных броней.
- Роль для DTO проверяется на сервере и не принимается из query-параметра, формы или клиентского состояния. Для авторизованного viewer роль повторно читается из базы до выборки данных владельцев.
- Считывание cookie и данных сессии должно оставаться за границей `<Suspense>` с учётом Cache Components; нельзя возвращать статическую оболочку с данными конкретного пользователя или с привязкой к `randomUUID()`.
- Подготовка строк/колонок и форматирование дат в UTC выполняются на сервере; клиент получает уже готовые строки, чтобы не было расхождения часовых поясов при гидратации.
- `ScheduleTable` — клиентский компонент только для открытия модальных окон. Он получает серверно подготовленные ячейки и флаг отображения владельца; этот флаг не является проверкой прав, а данные владельцев приходят только в административном DTO.
- После создания и изменения брони нужно инвалидировать не только `/slots`, `/bookings` и `/notifications`, но и `/`: главная теперь показывает те же слоты. После изменения слота администратором также инвалидируются `/` и `/slots`.
- `header` — серверный компонент в корневом layout; клиентских проверок ролей нет.
- Существующий `createBookingAction` переиспользуется без изменения контракта: `slotId` из формы, владелец и статус — на сервере, успех — `redirect('/bookings')`.
- `/admin/bookings/[id]` — новый защищённый маршрут. Он вызывает `requireRole(['admin', 'super_admin'])`, затем `getAdminBooking(actor, bookingId)`; функция повторно проверяет роль и возвращает `null` для неизвестного идентификатора, а страница вызывает `notFound()`. Публичный DTO расписания данных владельца не содержит; административный DTO доступен только при административной сессии.

## 10. Критерии приёмки

1. Гость открывает `/` и видит таблицу всех будущих слотов, а не только приветственную карточку.
2. `/` и `/slots` показывают одинаковое расписание и одинаковое поведение клика.
3. В таблице только будущие слоты в пределах 7 дней.
4. Колонки времени содержат только интервалы, в которых есть слот — свободный или занятый; пустых диапазонов `00:00–09:00` и `18:00–24:00` нет, если там нет слотов.
5. Пустые ячейки не содержат кнопок, текста и визуального заполнения; строки без слотов не выводятся.
6. Гость при клике по свободному слоту получает модальное окно с «Войти» / «Зарегистрироваться» / «Отмена»; бронь не создаётся.
7. Для гостя и `user` занятая ячейка содержит только неинтерактивный текст `Занято`; в HTML нет email, `displayName` и `User.id` владельца, нет ссылки на `/admin/bookings/[id]`.
8. `user`, `admin`, `super_admin` при клике по свободному слоту получают подтверждение; после подтверждения бронь `pending` и переход на `/bookings`.
9. `admin` и `super_admin` видят в занятой ячейке email, `displayName` (или `Без имени`), `User.id` и ссылку на `/admin/bookings/[id]`.
10. Ссылка из занятой ячейки открывает детализацию брони и не создаёт новую бронь; страница показывает владельца, слот, статус и даты, а действия подтверждения/отмены работают.
11. Прямой запрос `/admin/bookings/[id]` под `user` или гостем уводит на `/access-denied`; неизвестный идентификатор даёт `notFound()`.
12. Администратор может записаться на свободный слот для себя; управление остаётся в `/admin`.
13. `header` находится в `<body>`, а не в `<head>`; пункты соответствуют матрице ролей.
14. Гость видит «Расписание» и «Войти»; авторизованный пользователь видит свои разделы и «Выйти».
15. «Выйти» работает через Server Action; после выхода гость не видит защищённые пункты.
16. Модальные окна закрываются по «Отмена», `Esc` и клику по фону; фокус возвращается на кнопку; занятые ячейки модальных окон не открывают.
17. Прямой POST без сессии не создаёт бронь; роль и владелец не принимаются из формы.
18. Цветовая палитра не изменена; светлая и тёмная темы остаются рабочими.
19. `tsc`, lint, build и существующие тесты проходят; ручной smoke-тест гостя, `user`, `admin` и `super_admin` подтверждает сценарии.

## 11. Вне объёма

- Изменение цветовой палитры, шрифтов и общего визуального стиля.
- Новые модели, миграции, роли, статусы, внешние сервисы и зависимости.
- Email/SMS/push, OAuth, платежи, календарь, экспорт.
- Поиск, фильтры, пагинация, перенос и повторяющиеся слоты.
- Возврат к выбранному слоту после входа/регистрации.
- Редактирование брони или владельца прямо из ячейки расписания; управление пользователями и ролями.
- Переработка страниц `/admin`, `/admin/bookings`, `/bookings`, `/notifications`, `/account`, кроме добавления общего `header`, ссылки на детализацию и самой страницы `/admin/bookings/[id]`.

## 12. Проверки после реализации

- `npx tsc --noEmit`
- `npm run lint`
- `npm run build`
- `npm test`
- Ручной прогон: гость на `/` → модальное окно → `/login`; `user` → подтверждение → `/bookings`; `admin` → запись для себя и наличие «Администрирование»; `super_admin` → занятая ячейка → `/admin/bookings/[id]`; выход → гостевая навигация.
- Проверить исходный HTML: у гостя и `user` нет защищённых пунктов, email/`displayName`/`User.id` владельцев и ссылок на `/admin/bookings/[id]`; таблица содержит все слоты, включая занятые; у `admin` владелец и ссылка присутствуют; `<header>` находится в `<body>`.
- Проверить, что после создания, подтверждения и отмены брони, а также после изменения слота обновляются `/`, `/slots`, `/bookings`, `/notifications` и административные страницы.
