# AGENTS.md: Mini Booking System

## Контекст проекта

- Проект: локальный учебный Mini Booking System.
- Стек: Next.js 16 (App Router), React 19, TypeScript, Tailwind CSS 4, PostgreSQL, Prisma 8, Zod, `bcryptjs`, npm.
- Текущая фаза: нет активной. Последняя закрытая фаза — `4.3.4 simplified booking flow`; её план перенесён в `docs/archive/plans/`.
- `auth-lite` уже существует: регистрация, вход, сессия, роли и ровно один `seed`-пользователь с ролью `super_admin`.
- Слой данных `4.3.3` закрыт: модели `Slot`, `Booking`, `Notification`, серверные модули `app/lib/slots.ts`, `app/lib/bookings.ts`, `app/lib/notifications.ts`, seed 14 слотов на 7 дней вперёд.
- Границы закрытой фазы: пользователь видел свободные слоты, создавал и отменял свою бронь и читал свои уведомления; администратор управлял слотами и подтверждал или отменял брони. Отдельного сценария для `super_admin` в этом уроке нет.

## Правила auth-контура (сохраняются)

- Новая регистрация создаёт пользователя только с ролью `user`; роль не принимается из формы, query-параметра или тела запроса.
- Через `seed` создаётся ровно один пользователь с ролью `super_admin`.
- В базе хранится только `passwordHash`, а не пароль в открытом виде; хеширование — `bcryptjs.hash(password, 12)`, вход — `bcryptjs.compare(inputPassword, user.passwordHash)`.
- Сессия и роли проверяются на серверной стороне до рендера страницы или выполнения операции; скрытый элемент интерфейса защитой не считается.
- Модели `User` и `Session`, стандарт сессии и набор ролей не меняются.

## Правила booking flow `4.3.4`

- Горизонт слотов — 7 дней вперёд; один тип записи: одна активная бронь пользователя на слот.
- Слоты создаёт и редактирует администратор через защищённые серверные операции; пользовательским страницам доступно только чтение свободных слотов.
- Статусы брони только `pending`, `confirmed`, `cancelled`: создание даёт `pending`, администратор переводит `pending` → `confirmed` и `pending`/`confirmed` → `cancelled`; `cancelled` конечен.
- `user` видит и отменяет только свои брони и читает только свои уведомления. `admin` и `super_admin` видят все брони, подтверждают и отменяют их и управляют слотами.
- Владелец брони и автор действия берутся из действующей сессии; `userId`, роль и статус не принимаются из формы, query-параметра или тела запроса.
- Все операции выполняются через серверные модули `app/lib/slots.ts`, `app/lib/bookings.ts`, `app/lib/notifications.ts` и Server Actions; проверки роли и владельца обязательны внутри этих функций.
- Уведомление создаётся в той же транзакции, что и изменение брони: при создании брони и при каждом изменении статуса администратором; адресуется владельцу брони. Уведомления только внутренние.
- Бронь создаётся только на будущий слот при свободной вместимости; проверка вместимости и вставка атомарны, повторная активная бронь отклоняется.
- Идентификаторы и даты не выдумывать: seed и автотесты воспроизводимы и идемпотентны.
- Новые модели, миграции, статусы и роли — только после предварительного обновления `spec.md` и отдельного пункта `Plan.md`.

## Правила работы с Git

**Коммит и push выполняются только по прямому указанию разработчика.** По умолчанию агент не запускает `git commit` и `git push`: их выполняет сам разработчик. Прямое указание — это явная просьба в текущем сообщении, например «сделай commit and push». После каждой правки агент, независимо от наличия указания, даёт готовые команды для ручного запуска commit и push.

Разрешённые команды (только чтение, состояние репозитория не меняется):

- `git status`, `git diff`, `git log`, `git show`, `git ls-files`, `git check-ignore`, `git rev-parse`, `git remote -v`, `git branch --list`, `git ls-remote`, а также любые из них с `--no-pager`.

Запрещённые команды (меняют индексацию, локальную историю или удалённый репозиторий):

- По прямому указанию разработчика (по умолчанию не выполняются): `git commit` (в том числе `--amend`), `git push` (в том числе `--force`, `--delete`, `--tags`).
- Запрещено всегда, даже при просьбе в чате: `git tag`, `git remote add|remove|rename|set-url`, `git reset`, `git rebase`, `git revert`, `git cherry-pick`, `git merge`, `git checkout -b`, `git switch -c`, `git branch -d|-D`, `git stash drop|clear`, `git clean`, `git config` в режиме записи.
- `git add` — только по отдельной прямой просьбе разработчика и без последующего коммита.

Запуск линтера, сборки и автотестов разрешён: эти проверки не меняют состояние репозитория.

Порядок работы: агент вносит и проверяет изменения в рабочем дереве и оставляет их незакоммиченными. В итоговом отчёте он перечисляет изменённые файлы и даёт готовые команды для ручного запуска commit и push. Если прямого указания агенту не было, коммит и push выполняет разработчик сам.
